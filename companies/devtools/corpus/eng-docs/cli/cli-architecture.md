# gnt architecture

The `gnt` CLI is written in Go and lives in the `gnt` repository under the CLI & SDKs team. The binary is a thin shell: each subcommand is a package under `internal/cmd/`, and the top-level command dispatches based on the first argument. Shared logic (config loading, auth, API client, output formatting) lives in `internal/` packages that subcommands import. We keep subcommand packages deliberately small and push reusable code into `internal/`, so a new command usually means a new package plus a few lines in the dispatcher.

The plugin protocol lets teams extend `gnt` without touching the main module. A plugin is an executable named `gnt-<name>` on `PATH`; when a user runs `gnt <name>`, the CLI shells out and forwards the remaining arguments, working directory, and environment. Plugins receive the user's auth context through environment variables set by the CLI, so they can call the Gantline Cloud API without re-authenticating. We document the protocol in the repository README and keep a few internal plugins in the `plugins/` directory (for example, `gnt-codeowners` used by the Search team).

Config and auth are separate concerns. Config is a TOML file at `~/.config/gnt/config.toml` (or `%APPDATA%\gnt\config.toml` on {{DESKTOP_OS_2}}). It holds defaults like the API endpoint, the default workspace directory, and editor preferences. Auth profiles are stored separately under `~/.local/share/gnt/auth/` (or the platform equivalent). Each profile is a file named after the profile, containing an OAuth token, the token's expiry, and the profile's display name. The `gnt auth login` flow opens a browser and completes the device authorization flow against Gantline Cloud. `gnt auth switch` changes the active profile; `gnt auth list` shows profiles and which one is active. CI runners use a service account profile that is provisioned through the admin console.

Telemetry is opt-in. When a user has not expressed a preference, we prompt once during first run and store the choice in the config file. The telemetry payload covers command names, flags (with values redacted), exit codes, and rough timing. It is sent to the metrics pipeline at `telemetry.gantline.dev` over HTTPS, batched locally and flushed on a schedule. The CLI & SDKs team reviews the telemetry queries each quarter; the dashboards are in the metrics tool under "CLI telemetry". If telemetry is disabled, the CLI does not send anything and does not prompt again. Flag values that look like paths, URLs, or tokens are redacted client-side before batching.

Supported platforms: {{DESKTOP_OS_3}} (amd64, arm64), {{DESKTOP_OS_1}} (amd64, arm64), and {{DESKTOP_OS_2}} (amd64, arm64). We publish `gnt` through the package indexes and also provide standalone binaries attached to each release. Version numbering for the CLI follows `eng-docs/release/versioning.md`; the publishing steps for the binaries and the package updates are in `eng-docs/release/publishing-packages.md`.

The Python and TypeScript SDKs are generated from the OpenAPI spec that the API platform team maintains in the `api-spec` repository. The generator is a Go program in `internal/gen/` that reads the spec and emits both SDKs. We run the generator as part of the nightly build for the CLI & SDKs pipeline; the generated code is committed to the `sdk-python` and `sdk-typescript` repositories so consumers get stable diffs. The generator output includes typed request/response models, a client class, and per-endpoint methods. Hand-written additions live in `overlay/` files inside the generator repository and are merged after generation. We avoid editing generated files directly; if a fix is needed in the output, it goes into the generator or the overlay. Elif and Karim review generator changes in code review; Jonas maintains the Python SDK and Kalani maintains the TypeScript SDK.
