# Editor overview

The web editor and the desktop app share a single codebase, with the desktop shell adding native window management, local file access, and offline support. Both targets are built from the same source tree and most feature work lands in both at the same time. The desktop app is distributed through the normal release train; the web editor ships with the Gantline Cloud frontend.

The extension host runs in a separate process (or a separate web worker in the browser) and communicates with the editor core over a JSON-RPC protocol. Extensions are written against the same API surface in both environments, though extensions that require node APIs only work in the desktop app. The extension host manages activation events, command registration, and the lifecycle of individual extensions.

Language servers run inside the workspace, not in the editor process. For cloud workspaces this means the server processes run on the same VM as the user's code, so they can read files directly from disk and respond to edits without any network round trip beyond the workspace connection. For local desktop workspaces, the language servers are spawned as child processes of the extension host. We support the usual set of servers — TypeScript, Go, Python, Rust, Java, and a few others — and the workspace startup sequence pre-warms the ones configured for the repository's detected language. If a server crashes, the extension host restarts it and re-issues the open-file requests; the UI shows a brief notice in the status bar.

Settings sync uses the same backend as the rest of Gantline Cloud. A user's editor settings, keybindings, snippets, and UI state are stored per-account and applied when the editor starts in a new workspace or on a fresh desktop install. Sync is keyed by the signed-in Gantline identity and does not depend on the workspace's git identity. Conflicts between two devices that changed the same setting are resolved by last-write-wins, which is fine for settings but occasionally surprises people who edit the same JSON file from two machines; the sync log in the settings panel shows what changed and when.

Crash reports from the desktop app are uploaded to the same crash ingestion pipeline we use for the mobile apps. The desktop app captures the stack trace, the editor version, the OS version, and the last few actions from the command palette, and uploads it after the next launch. Reports are grouped by signature in the crash dashboard, and the Editor team triages the top groups each week. There is no automated upload of user files or workspace contents; crash payloads are limited to the metadata above plus any log lines the extension host has already written to its own log buffer.

The editor team owns the codebase under `editor/`, and most changes go through the usual review process. The web editor is served from the main cloud frontend, so any change to the browser-side code follows the frontend deploy schedule. Desktop releases follow the desktop release train and are announced in #releases. For questions about the extension API, the language server protocol, or crash report triage, ask in #editor.
